# AGENTS.md — правила разработки ЯМузыканта

Правила обязательны для всех агентов и людей. Нарушение §1–§6 — причина вернуть PR без детального ревью.

## 1. Роли

| Роль | Кто | Отвечает | Не делает |
|---|---|---|---|
| ORCH — оркестратор | агент, модель `opus` | выбирает задачи, запускает исполнителей и ревьюеров, мержит, ведёт статусы, проводит гейты | не пишет продуктовый код |
| IMPL — исполнитель | агент, модель из `model_impl` карточки | одна задача: тесты → код → PR | не берёт вторую задачу, не меняет объём |
| REV — ревьюер | агент, модель из `model_review`, **новый контекст** | проверка PR по `docs/02-process/REVIEW.md` | не правит код (только комментарии и вердикт) |
| QA — визуальная и e2e-проверка | агент `sonnet` | сравнение с эталонами, a11y, сценарии UC | |
| OWNER — владелец | человек | секреты, подпись гейтов, юридические тексты, «уточнить» | |

Специализации исполнителя: `BACK` (Laravel, домен, очереди, интеграции), `FRONT` (Inertia-страницы, React, ДС), `DB` (миграции, индексы, сиды), `DEVOPS` (CI/CD, окружения), `SEC` (безопасность, ПДн). Поле `roles` карточки — какие специализации нужны. Если ролей несколько, исполнитель один, а порядок работы такой: DB → BACK → FRONT.

## 2. Цикл работы (SDD + TDD)

Подробно — `docs/02-process/SDD-TDD.md`. Коротко:

1. **Spec.** Работа — только по карточке `docs/tasks/*.md` в статусе `ready`. Нет карточки — оркестратор создаёт её по шаблону до кода.
2. **Red.** Сначала тесты по каждому критерию приёмки, отдельным коммитом `test(N.M.K): …`. В CI видно, что они падали до реализации.
3. **Green.** Минимальный код, чтобы тесты прошли. Коммиты `feat(N.M.K): …`.
4. **Refactor.** Чистка без изменения поведения, тесты зелёные.
5. **Design check.** Для задач с `prototype`: визуальный тест против эталона из `design/screens`, проверка 8 состояний, axe.
6. **PR.** Шаблон `.github/pull_request_template.md`, ссылка на issue (`Closes #N`), скриншоты реализации рядом с эталоном.
7. **Review → merge.** Ревьюер другой модели или в новом контексте. Мерж — squash, только при зелёном CI и вердикте `approve`.

Одна задача = одна ветка `task/N.M.K-slug` = один PR. PR больше ~600 строк без тестов и сгенерированных файлов — сигнал разбить задачу.

## 3. Definition of Ready / Done

**Ready:** у карточки есть цель, критерии приёмки, роли, модели, гейт; все `depends_on` в статусе `done`; есть ссылки на UC и макет (если это экран).

**Done:**
- [ ] каждый критерий приёмки покрыт тестом, тесты зелёные;
- [ ] Pint, Larastan (уровень 8), ESLint, `tsc --noEmit`, `lint:copy`, `docs:check` — без ошибок;
- [ ] для экранов: визуальное расхождение с эталоном ≤ порога из `DESIGN-SYSTEM.md §6` на 1440 и 390 px; 8 состояний интерактивных элементов; axe без нарушений уровней serious и critical;
- [ ] миграции обратимы или откат описан в PR; новые переменные окружения — в `.env.example` и `ARCHITECTURE.md §9`;
- [ ] вердикт ревьюера `approve`; карточка `status: done`, `sync_state: aligned`; `npm run docs:refresh` выполнен.

## 4. Код

**PHP / Laravel**
- `declare(strict_types=1)` везде. Larastan уровень 8, Pint (пресет laravel).
- Домен — `app/Domain/{Context}/` (Actions, Models, Enums, Events, Policies, StateMachines). Контроллеры тонкие: валидация (Form Request) → Action → ответ Inertia.
- Статусы — PHP enum. Переходы — только через `*StateMachine`; прямое `->update(['status' => …])` запрещено (проверяется тестом-архитектурой Pest `arch()`).
- Права — Policies + spatie/laravel-permission. Данные наружу — только через API Resources / Inertia props с явным списком полей. Телефон, ИНН, полный серийный номер не уходят на фронт.
- Деньги — целые рубли (`int`), без float.
- Очереди — для всего, что дольше 200 мс: фото, индексация, письма, автопроверки.
- Время — UTC в БД, `Europe/Moscow` в отображении.

**TypeScript / React**
- `strict: true`, без `any`. Страницы — `resources/js/Pages/**` (Inertia), общие блоки — `resources/js/Components`, раскладки — `resources/js/Layouts`.
- UI — только из `@ds` (дизайн-система) и `resources/js/Components` (композиции компонентов ДС на токенах). Сырые `<button>`, `<input>` со своими стилями — только внутри `Components` с обоснованием в PR.
- Стили — только токены `var(--*)` ДС и классы `ym-*`. Hex, rgb и произвольные px-значения цветов в коде страниц запрещены (ESLint-правило и `lint:copy --styles`).
- Тексты интерфейса — в `lang/ru/*.php` (бэкенд) и `resources/js/lang/ru.ts` (фронт), чтобы их проверял `lint:copy`.

**Общее**
- Conventional Commits: `test(2.1.1): …`, `feat(2.1.1): …`, `fix:`, `refactor:`, `docs:`, `ci:`.
- Новые зависимости — только с записью в PR: зачем, альтернативы, лицензия.
- Секреты — только GitHub Secrets / хранилище окружения. `.env` не коммитится.
- Не трогать: `resources/js/ds/**` (обновляется только `npm run ds:sync`), `docs/operations/status/**`.

## 5. Текст интерфейса

- Обращение на «вы», коротко, глагол в кнопке первым, без восклицательных знаков и эмодзи. Ошибки: что случилось + что сделать.
- Цены: `184 500 ₽` (неразрывный пробел), диапазон `168 000 – 196 000 ₽`. Даты: `3 окт`, в документах — `ДД.ММ.ГГГГ`.
- Название — «ЯМузыкант», склоняется: «на ЯМузыканте».
- **Запрещённые слова** (проверяет `tools/lint-copy.mjs` в исходниках и e2e-тест `copy.spec.ts` в отрисованном DOM):

| Нельзя | Пишем |
|---|---|
| гир, мой гир | инструмент, мои инструменты, оборудование |
| сетап | настройка |
| Ля440 | Цены продаж |
| Фермата | Безопасная сделка (в MVP не показываем) |
| По рукам! | Цена согласована |
| Кофр-доставка | Доставка в защитной упаковке |
| Ладмастер, Ладмир | ЯМузыкант |

## 6. Дизайн

Полные правила — `docs/03-design/DESIGN-SYSTEM.md`. Главное:
- Компоненты ДС используются как есть, с пропсами из `.d.ts`. Нужно другое поведение — задача на изменение ДС в её репозитории, а не форк в проекте.
- Логотип — `Wordmark` ДС; «Я» отдельным цветом не выделять.
- Светлая тема везде; тёмная — только внутри `[data-theme="dark"]`.
- Каждый экран сверяется с эталоном `design/screens/{id}@{1440|390}.png`. Отличия, принятые OWNER, фиксируются в `design/DEVIATIONS.md`.

## 7. Чего не делать

- Расширять объём задачи. Соседнее улучшение — новая карточка (оркестратор создаёт её со статусом `todo`).
- Придумывать цифры, сроки, юридические тексты. Неизвестное — «уточнить» в карточке и вопрос OWNER.
- Отключать или ослаблять тесты и проверки, чтобы CI стал зелёным.
- Мержить свой PR самому себе. Ревьюер не может быть исполнителем той же задачи.
- Делать функции вне MVP (`SPEC.md §2`), даже «заодно».
