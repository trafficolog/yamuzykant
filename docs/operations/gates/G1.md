- Reverb (0.1.16), после 0.1.12 (stage-сервер) — в репозитории всё готово, на сервере не проверено:
  - Секреты окружения `REVERB_APP_ID`, `REVERB_APP_KEY`, `REVERB_APP_SECRET` в `stage` и `production` (разные значения); без них `deploy.sh` ставит `BROADCAST_CONNECTION=null` — это штатный режим, а не ошибка
  - После выкатки `provision.yml` (`provision`) — на сервере обновлены Nginx (`location /app/`) и Supervisor; `supervisorctl status ymuzykant:ymuzykant-reverb` — RUNNING, `ss -ltn | grep 8080` слушает только `127.0.0.1`
  - `deploy/bin/smoke-reverb.sh <домен stage> <REVERB_APP_KEY>` (`SMOKE_BASIC_AUTH` — пароль stage) печатает `OK`
  - Сообщение, отправленное в одной вкладке, появляется во второй вкладке (другой пользователь) ≤ 2 с; результат записать в файл сессии
  - Браузер не показывает ошибок wss в консоли; stage закрыт паролем — проверить, что соединение `/app/` проходит с кэшированными учётными данными basic-auth, иначе открыть `/app/` в Nginx для stage по запросу `Upgrade: websocket`
  - Выкатка без Reverb (секреты сняты): `BROADCAST_CONNECTION=null`, `failed_jobs` без заданий трансляции
  - Лимит файлов: `cat /proc/$(pgrep -f reverb:start | head -1)/limits | grep 'open files'` ≥ 10000; без расширения `ext-uv` Reverb держит не более 1024 соединений (`stream_select`) — при росте нагрузки установить `ext-uv`
  - Production: то же после первого `release.yml`, `REVERB_ALLOWED_ORIGINS` — домен production
- Перед миграцией `listings_one_draft_per_user` проверить дубли черновиков: `SELECT user_id FROM listings WHERE status='draft' GROUP BY user_id HAVING count(*)>1` (2.1.4)
- В `.env` stage `CACHE_STORE=redis`: на нём держатся метка «в сети» и частота писем `Cache::add` (4.4.1)
- До переключения кода на stage — `php artisan scout:sync-index-settings` (новый `sortableAttributes: id`, 3.1.12): иначе запросы с `sort: id:desc` падают и «Похожие» пусты

- Наблюдаемость на stage (0.1.14, после 0.1.12 и после того, как OWNER задаст `SENTRY_LARAVEL_DSN` и `VITE_SENTRY_DSN`): (1) тестовое исключение из запроса и из задания очереди видно в Sentry с `release` = sha выката и тегом `request_id`, совпадающим с `X-Request-Id` ответа; (2) событие из браузера несёт тот же `request_id` из `<meta name="request-id">`; (3) в событии нет e-mail, кода входа и строковых аргументов кадров приложения (`[string:N]`); (4) `curl -i https://<stage>/health` снаружи: только `{"status":…}`, без `Set-Cookie`; с `X-Forwarded-For: 127.0.0.1` — тоже без `checks`; (5) `HEALTH_TOKEN` задан в `.env` stage, с заголовком `X-Health-Token` видны `checks`; (6) каталог счётчиков лимита `/health` доступен пользователю php-fpm: `sudo -u <пользователь php-fpm> sh -c 'touch <каталог релиза>/storage/framework/cache/.w && rm <каталог релиза>/storage/framework/cache/.w' && echo ok`; (7) `zend.exception_ignore_args=On` и в php-fpm, и в CLI: `php -i | grep exception_ignore_args` и `php-fpm<версия> -i | grep exception_ignore_args` (или `php-fpm -tt`) — оба `On`. Как вызвать тестовое исключение (в `php artisan tinker` в каталоге релиза, `.env` stage): из запроса — `Route::get('/_sentry-check', fn () => throw new RuntimeException('sentry-check')); app()->handle(Illuminate\Http\Request::create('/_sentry-check', 'GET', [], [], [], ['HTTP_X_REQUEST_ID' => 'sentry-check-0001']));` — событие должно прийти с тегом `request_id=sentry-check-0001`; из задания — `Illuminate\Support\Facades\Context::add('request_id', 'sentry-check-0002'); dispatch(fn () => throw new RuntimeException('sentry-check-job'));`, затем один `php artisan queue:work --once` (воркер systemd подхватит и сам); `php artisan sentry:test` проверяет только доставку и DSN, request_id в нём нет. Результат — в файл сессии 0.1.14 (скриншот или ссылка на событие)
